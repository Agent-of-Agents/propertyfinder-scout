# Scout Dubai — система подбора недвижимости Алексея Широкова

Дубай (Property Finder, Bayut) · центр Москвы и Рублёвка (Циан, Яндекс) · дистресс-объекты.
Один агент **Scout Dubai**, модель клиент → подбор → объект, Telegram-группа с темой на клиента.

Документы: чертёж системы — `docs/system-blueprint.html`; как выглядит в Telegram —
`docs/scout-dubai-telegram.html`; спецификация агента — `docs/HANDOFF.md`.

## Репозиторий и стандарт фабрики

Репозиторий создан фабрикой агентов (agent-builder-mcp) по её стандарту: LangChain v1
`create_agent`, `agent.py` с `build_agent()`, реестр `tools/TOOLS`, `middleware/`,
`memory.py` (MongoDB), `bot.py` (aiogram, long polling), смоук-тесты в `tests/`.

**Автодеплой — неприкасаемый стандарт.** Push в `main` → GitHub Actions
(`.github/workflows/deploy.yml`) → rsync на сервер в `/opt/agents/propertyfinder-scout`
→ `docker compose up -d --build` → проверка, что контейнер выжил. Не менять:
`.github/workflows/deploy.yml`, `Dockerfile`, `docker-compose.yml`, способ создания `.env`
на сервере. Любая правка этих файлов — только по прямому решению Алексея.

Из этого следуют два ограничения для кода:
- **В контейнере нет тома.** Пересборка стирает файловую систему. Состояние (карточки
  клиентов, `state.json` сверки, кэш каталога проектов) должно жить в MongoDB
  (`MONGODB_URI` уже в стандарте) или на Google Диске, не в файлах контейнера.
- **Секреты — только через `.env` на сервере.** Ключ сервисного аккаунта передаётся
  как переменная окружения, не как файл в образе.

Разделение кода:
| Где | Что | Чьё |
|---|---|---|
| `agent.py`, `bot.py`, `config.py`, `memory.py`, `middleware/`, `schemas.py`, `main.py` | обвязка агента | стандарт фабрики; расширяем (темы, кнопки, планировщик), не ломая контракт `python bot.py` |
| `tools/scout_*.py` | LangChain-инструменты — тонкие обёртки над `scout.actions` | наше |
| `scout/` | прикладной слой: хранилище (MongoDB/файлы), модель клиент → подбор, книги, карточки, действия, прогон | наше |
| `lib/` | вся предметная логика: PF, Google, сверка, PDF, дистресс, офф-план | наше, без зависимостей от LangChain |
| `scripts/` | CLI для ручного запуска и локального прогона | наше |
| `assets/` | шрифты, шаблон страницы WhatsApp, рендеры проектов | наше |
| `docs/` | чертёж, схема Telegram, HANDOFF | наше |

Ветки: работа в feature-ветках, в `main` — через PR. Merge в `main` = деплой на сервер.

### Два ограничения, которые важно помнить

**1. У сервисного аккаунта нет своего места на Диске.** Файл, который он создаёт,
принадлежит ему и упирается в нулевую квоту — `storageQuotaExceeded`.
Поэтому таблицы создаются **от имени Алексея**, а сервисный аккаунт их только
редактирует; прав редактора ему достаточно. `drive.create_spreadsheet_in_folder`
ловит эту ошибку и объясняет варианты.

Для работы на сервере без человека нужен **Общий диск (Shared Drive)**: там квота
принадлежит организации, и сервисный аккаунт сможет создавать файлы сам.
Это к этапу 4.

**2. Запись в живую таблицу — только по своим колонкам.** Система пишет в свои
колонки через `sheets.update_ranges`, колонки Алексея (галочка «Одобрено», статус,
его цена, его комментарий) не трогает никогда. Якорь строки — скрытая колонка A
со стабильным `listing_id`.

## Off-plan: проекты застройщиков

Решение 11.09.2026: платные каталоги (Reelly $500/мес, Alnair, TrendAgent) не берём.
Источник — раздел **Property Finder «New projects»**: `/en/new-projects/lp/dubai`,
JSON в `__NEXT_DATA__`, как и у объявлений. ~1 100 проектов застройщиков по Дубаю.
Что там есть: застройщик, район, фаза продаж (`waiting_for_sales_start` = пресейл,
`booking_started`), дата старта продаж, сдача, платёжный план по фазам, цена «от»
по типам квартир с площадями, сделки DLD по локации, **брошюра застройщика**
(`brochureUrl`), рендеры, планировки по типам, генплан. Чего нет: наличия по
конкретным юнитам (не нужно).

Данные: `data/pf_projects/` — список на дату, кэш карточек `details/<id>.json`
(перечитывается при смене цены/фазы/сдачи или раз в 14 дней), итог `projects.json`.
Полный первый сбор ~45 минут, дальше ~5–10 минут.

Бриф клиента — блок `"offplan"` в `client.json` (поля — в докстринге `lib/offplan.py`):
`bedrooms`, `budget.max`, `communities`, `delivery_by`, `developers`,
`post_handover`, `max_down_payment`, `launches_only`. Единица подбора —
**проект × тип квартиры**, `listing_id = project_id:тип`. Лист «Off-plan» живёт
по тем же правилам, что «Объекты»: новые сверху голубым, 💰 изменения, ⚰️ выбывшие,
колонки Алексея (✅ Одобрено, Статус, Мой комментарий) не трогаем.
`daily.py` обновляет каталог один раз за прогон и сверяет лист у каждого клиента
с блоком `offplan`.

У клиента может быть **несколько брифов** (`"offplan": [ {...,"sheet": "Dubai Islands"}, ... ]`) —
по листу на каждый. Жёсткое денежное условие — `pre_handover_cash_max` (цена × доля
плана до ключей); пожелания по плану (`prefer_pre_handover_max`, `prefer_handover_min`,
`prefer_post_handover_min`) — мягкие, дают балл. Пример — `clients/<дата>_<slug>/client.json` (папка `clients/` в git не хранится).

**Оформление листов** — `offplan_sheet.style_sheet`: тёмная шапка, закреплены шапка и
колонки до «Проект» (для «Объектов» — до «Брокер»), ширины и форматы по названию колонки,
шкала балла. Применяется при каждой сверке и к каталогу; только форматирование.

**Презентации off-plan** — `scripts/make_offplan_presentation.py --client x`: рендеры и
планировки с PF (чистые, без водяных знаков), платёжный план с суммами от цены «от»,
папка на Общем диске «<Клиент> — Off-plan / <лист> / <проект · тип · от цена>». Цена —
«from» застройщика, своей цены у off-plan нет. `daily.py` собирает их после сверки.

Скоринг объясняемый (0–100, причины в «Комментарий системы»): цена за м² против
медианы района по типу и против сделок DLD, стадия (пресейл +), взнос и
post-handover, срок сдачи. Веса — в `lib/offplan.score`, править по отзывам Алексея.

## WhatsApp: запросы брокерам

Property Finder не отдаёт личный номер агента. Кнопка WhatsApp в объявлении ведёт
на **общий шлюз PF** — один и тот же номер `+971 4 556 0345` у всех объявлений,
а в предзаполненном тексте стоит: «Any changes made to this message will result in
the enquiry not being sent to the agent». **Текст менять нельзя** — иначе запрос
до агента не дойдёт. Свои вопросы задаются потом, в ответной переписке.

`broker.phone` из выдачи — живой номер агентства, но почти половина из них
офисные landline `+9714…`, где WhatsApp обычно нет.

**Отправляет человек.** У приложения WhatsApp Business нет API; программная
отправка возможна только через Cloud API, а перевод номера туда отключает
приложение на этом номере. Поэтому цикл такой:

1. Алексей ставит галочки в колонке «📩 Запросить»
2. `scripts/send_requests.py` собирает свежие ссылки и делает страницу
3. Страница публикуется артефактом, открывается на телефоне — один тап на объект
4. Скрипт проставляет дату в колонку «Запрошено» и снимает галочки

Отметки об отправке живут в localStorage браузера, ключ — по имени листа и дате.
